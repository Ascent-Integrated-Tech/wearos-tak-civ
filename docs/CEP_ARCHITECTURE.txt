CEP Architecture – Design and Runtime Flow

1) Overview
- Purpose: The CEP (Complex Event Processing) module consumes measured signals from wearable sensors and environment services, derives features, evaluates rules against those features, and triggers actionable alerts with robust duplicate suppression and automatic cancellation.
- Core building blocks:
  - cep_rules.json: Declarative configuration for features and rules.
  - Bus: CepBus (hot stream for incoming sensor/events).
  - Stores: FeatureStore (point-in-time KV with timestamps) and WindowStore (rolling rings for windows).
  - Engine: CepEngine orchestrates ticks, feature computation, rule evaluation, and alert clearing.
  - Rules: RuleEngine compiles/evaluates conditions and dispatches actions.
  - Actions: Action handlers (LogActionHandler) post alerts via EventBus and de-duplicate via AlertRegistry.
  - Cancellation: Exit conditions per rule drive automatic cancel with the same UID to clear TAK markers.


2) cep_rules.json – Structure and Semantics
Top-level keys:
- engine: Global engine config.
  - window_tick_ms: Tick period in milliseconds. CepEngine converts to tickHz as 1000 / window_tick_ms (min 1 Hz).

- features: Array of feature definitions. Each element has a type and type-specific fields. Features are either:
  - Measured (raw) → Stored directly by WindowStore.ingest() into FeatureStore under well-known keys.
  - Derived (computed) → Produced from windows, deltas, and/or expressions, written via FeatureStore.putDerived().

  2.1 Measured features (ingested streams)
  - Source: Services publish CepEvent(topic, payload) to CepBus; CepEngine subscribes and forwards to WindowStore.ingest().
  - Storage: WindowStore writes the latest measured values into FeatureStore under well-known keys and updates rolling rings for windowed computations.
  - Numeric streams (examples; written via FeatureStore.put):
    - "heart_rate"              ← HeartRatePayload.bpm
    - "ambient.temp_c"          ← AmbientPayload.temp_c
    - "ambient.humidity_pct"    ← AmbientPayload.humidity_pct
    - "ambient.wind_mps"        ← Ambient/WindPayload.speedMps
    - "accel.magnitude_g"       ← AccelPayload.magnitude_g
    - "accel.cadence_spm"       ← AccelPayload.cadence_spm
    - "hrv.rmssd_ms"            ← HrvPayload.rmssd_ms
    - "gyro.rms_dps"            ← GyroPayload.rms
    - "ppg.amplitude"           ← PpgPayload.amplitude
    - "humidity.relative_percent" ← HumidityPayload.relativePercent
    - "light.lux"               ← LightPayload.lux
    - "offbody.on_wrist"        ← OffBodyPayload.on_wrist (Int)
  - Boolean/categorical streams:
    - "activity.state"          ← ActivityPayload.state (string label)
    - "sleep.is_sleeping"       ← SleepPayload.is_sleeping (boolean)
    - "immersion.wet_flag"      ← ImmersionPayload.wet_flag (boolean)
    - "immersion.immersion_flag"← ImmersionPayload.immersion_flag (boolean)
    - "als.covered"             ← LightPayload.covered (boolean, if provided)
  - Array streams (multi-channel):
    - "skin_temp"               ← SkinTempPayload.c_peripheral (e.g., [wrist, hand]) held in WindowStore.arr for multi-window/slope operations.
  - Naming: Measured keys are not auto-prefixed with "features." (they are raw names). Derived outputs usually appear under "features.<id>".

  2.2 Derived feature types – detailed descriptions and examples
  - type="window"
    - What: Aggregation over the trailing time window of a numeric stream. Conceptually, it consumes the most recent N seconds of samples and applies an operation (op) to summarize that window.
    - Inputs: source (numeric stream key), window_sec, op ∈ {min,max,avg,rms,median}.
    - Output: Single numeric value per tick written to features.<id>.
    - Stream requirements: The source must be a numeric time series kept in WindowStore.num (i.e., a measured numeric stream ingested via CepBus → WindowStore.ingest).
    - Edge cases: If there are insufficient samples in the ring for the requested window, or no data, the value is null this tick.
    - When: To smooth noisy signals or compute robust rolling statistics (e.g., 60s avg HR), or to bound/denoise thresholding inputs used in rules.
    - Example:
      {
        "id": "hr_avg_60s",
        "type": "window",
        "source": "heart_rate",
        "op": "avg",
        "window_sec": 60
      }

  - type="window_multi"
    - What: Aggregation across a multi-channel array stream per sample, then across time. Conceptually, each sample is an array of channels; we first reduce each sample to a single value (multi_policy), then aggregate over time (op).
    - Inputs: source (array stream key, e.g., "skin_temp"), multi_policy ∈ {"min","max"}, window_sec, op ∈ {min,max,avg,rms,median}.
      • multi_policy chooses how to reduce each sample’s channels (e.g., per-sample min), producing a single series before applying op across time.
    - Output: Single numeric value per tick to features.<id>.
    - Stream requirements: The source must be an array series kept in WindowStore.arr. If empty or missing, the value is null.
    - When: For sensors with multiple channels (e.g., multiple skin temp placements) where you care about worst/best channel behavior.
    - Example:
      {
        "id": "skin_temp_min_channel_avg_120s",
        "type": "window_multi",
        "source": "skin_temp",
        "multi_policy": "min",
        "op": "avg",
        "window_sec": 120
      }

  - type="slope_multi"
    - What: Time slope (trend) over a chosen channel of an array stream using least-squares. Conceptually, select one channel (based on last sample and multi_policy), then fit a line through the last window_sec of values and report its slope.
    - Inputs: source (array stream key), multi_policy ∈ {"min_channel","max_channel"}, window_sec, units_per_sec ∈ {"per_second","per_minute"}.
      • multi_policy selects which channel to follow over time based on the last sample (e.g., min_channel picks the channel with the lowest last value).
    - Output: Numeric slope (units per second or per minute) to features.<id>.
    - Stream requirements: Requires an array stream with enough samples; null if insufficient data.
    - When: Detecting upward/downward trends on the most at-risk channel (e.g., dropping skin temp).
    - Example:
      {
        "id": "skin_temp_min_channel_slope_5min",
        "type": "slope_multi",
        "source": "skin_temp",
        "multi_policy": "min_channel",
        "window_sec": 300,
        "units_per_sec": "per_minute"
      }

  - type="delta"
    - What: Difference between the latest numeric value and the value horizon_sec in the past. Conceptually, it answers “how much has this signal changed over the last horizon_sec seconds?”
    - Inputs: source (numeric stream key), horizon_sec.
    - Output: Numeric difference to features.<id>.
    - Stream requirements: The source must be a numeric series in WindowStore.num; if the ring cannot provide the historical sample for the specified horizon, the output is null.
    - When: Quantify change over time (e.g., HR delta over 2 minutes).
    - Example:
      {
        "id": "hr_delta_2min",
        "type": "delta",
        "source": "heart_rate",
        "horizon_sec": 120
      }

  - type="derived"
    - What: Rich DSL for computed features; supports specialized handlers, numeric operators, boolean logic, categorical mapping, and legacy JsonLogic fallback. Conceptually, “derived” composes values already present in FeatureStore (including outputs of other features from this tick) to create new signals.
    - Inputs: expr (JSON object). See section 2 and DerivedEval for operators/handlers.
    - Output: Numeric, boolean, or string written to features.<id> depending on the expression.
    - Data sources: Can reference any key accessible via FeatureStore (e.g., measured keys like "heart_rate" or other derived outputs such as "features.hr_avg_60s").
    - When: Flexible compositions (e.g., Karvonen ratios, wind-chill, categorical risk).
    - Example (numeric math):
      {
        "id": "hrr_ratio",
        "type": "derived",
        "expr": { "karvonen_ratio": {
          "hr_key": "features.heart_rate",
          "rest_key": "profile.hr_rest_bpm",
          "max_key": "profile.hr_max_bpm",
          "min_den": 1.0
        }}
      }
    - Example (categorical):
      {
        "id": "cold_risk_state",
        "type": "derived",
        "expr": { "categorical": {
          "key": "features.cold.score",
          "bins": [0, 4, 7, 11],
          "labels": ["NORMAL", "WARN", "ALERT", "EMERGENCY"]
        }}
      }

  2.3 Can "window" operate on derived outputs?
  - Short answer: Not by default. The "window" feature reads from WindowStore.num, which contains numeric rings populated from measured streams during ingest. Derived outputs are written to FeatureStore but are not added to rings.
  - Recommended patterns:
    1) Window raw signals, then derive from windowed results.
       • Example: compute hr_avg_60s with type=window, then in a type=derived expression use {"key":"features.hr_avg_60s"} as input to further math or categorization.
    2) Decompose a complex derived window into windowed primitives.
       • Example: Instead of windowing a ratio directly, compute windowed HR and then compute the ratio against static profile keys (rest/max) in type=derived.
  - Advanced options (require code changes):
    • Extend WindowStore to maintain rings over selected derived outputs (not present in current code).
    • Introduce a new feature type (e.g., "window_derived") that mirrors "window" but explicitly consumes derived keys and feeds them into a managed ring.
  - Practical guidance: In the current implementation, design pipelines as: measured → window (numeric/array) → derived (compose windowed results). This yields stable inputs for rules without extra engine complexity.

Feature types (as parsed in RuleCompiler.parseFeatures → CepConfig.FeatureDef):
- type="window"
  - id: Identifier for the derived feature (written under features.<id> by convention).
  - source: Name of a numeric stream held in WindowStore.num (e.g., "heart_rate", "accel.cadence_spm").
  - op: Aggregation over the trailing window: one of "min", "max", "avg", "rms", "median".
  - window_sec: Window width in seconds; realized as window_sec * tickHz samples from the ring.
  - Computation: WindowStore.computeWindow()

- type="window_multi"
  - id
  - source: Name of an array stream held in WindowStore.arr (e.g., skin temperatures as [wrist, hand]).
  - multi_policy: "min" or "max" – how to condense per-sample arrays into a single channel before op.
  - op: Same set as "window".
  - window_sec
  - Computation: WindowStore.computeMultiWindow()
    - Example: For skin temp channels, choose min channel per sample, then aggregate min/avg/… across time.

- type="slope_multi"
  - id
  - source: Array stream key.
  - multi_policy: e.g., "min_channel" or "max_channel" – which channel to follow for time-slope.
  - window_sec
  - units_per_sec: "per_second" or "per_minute" – scaling for slope per second/minute.
  - Computation: WindowStore.computeSlopeMulti() (least-squares slope along chosen channel’s series).

- type="delta"
  - id
  - source: Numeric stream key in WindowStore.num.
  - horizon_sec: Difference of current value and the value horizon_sec in the past.
  - Computation: WindowStore.computeDelta()

- type="derived" (general expression DSL)
  - id
  - expr: JSON object that can represent numeric expressions, boolean logic, categorical mapping, or specialized forms. Evaluated by DerivedEval.eval().
  - Specialized handlers supported (examples):
    - { "wind_chill": { "temp_key": "ambient.temp_c", "wind_key": "ambient.wind_mps" } }
    - { "zone_min_bpm": { "lower_pct": 0.50, "profile_rest_key": "profile.hr_rest_bpm", "profile_max_key": "profile.hr_max_bpm" } }
    - { "mark_state": "activity.state" }  // marks last-true timestamp in StateRepo
    - { "karvonen_ratio": { "hr_key": "...", "rest_key": "profile.hr_rest_bpm", "max_key": "profile.hr_max_bpm", "min_den": 1.0 } }
  - Numeric operators:
    - key lookup: { "key": "<features.some_key>" }
    - div, mul, sub, add, max, min, sum, case (first matching branch; optional else)
  - Boolean operators:
    - lte, gte, lt, gt, eq
    - and, or, not
    - ref/is: { "ref": "<key>", "is": <value> } for exact match on bool/string/number
  - Categorical mapping:
    - { "categorical": { "key":"<features.some_score>", "bins":[0,4,7,11], "labels":["NORMAL","WARN","ALERT","EMERGENCY"] } }
  - Fallback: If none of the above match, DerivedEval delegates to JsonLogic.eval() for legacy logic.


- rules: Array of rule definitions. Parsed in RuleCompiler.parseRules → CepConfig.RuleDef/CepConfig.RuleAction.
  - id: Unique rule identifier (also used by AlertRegistry for de-dup per rule).
  - description: Optional human-readable description.
  - when: Condition JSON evaluated via JsonLogic (see below).
  - sustained_for_sec: Minimum consecutive seconds the condition must remain true before the rule fires. Implemented by TriggerTimer.
  - hold_down_sec: Minimum cooldown seconds before the rule can fire again. Implemented by TriggerTimer.
  - action: Object describing what happens when the rule fires:
    - type: Handler key (e.g., "log"), dispatched via CepActionDispatcher → LogActionHandler.
    - severity: "INFO" | "WARN" | "ALERT" | "EMERGENCY" (also influences dispatcher throttle and default priority).
    - message: Text included in emitted alert.
    - tags: String list used in dispatcher de-dupe key.
    - category: Alert category string sent downstream (e.g., "CAT_HR_ALERT").
    - isTak: If true, handler posts CustomEmergencyEvent to EventBus for TAK/Ditto.
    - isLocal: If true, reserved for local UI feedback.
    - priority_from: Usually "severity" (maps severity → priority int); optional explicit priority.
    - priority: Optional override when not deriving from severity.
    - sendSms: Optional downstream behavior toggle.
    - timeout: Optional legacy cancel timeout (commented in handler; exit-based cancel is primary path).
    - uid: Optional explicit UID; if blank/absent a new UID is generated when first firing.
    - monitor: Array of exit conditions for auto-cancellation (see ExitCondition below).
      - Each entry: { "feature": "<key>", "exit_below": <num|null>, "exit_above": <num|null>, "hysteresis": <num> }
      - Hysteresis is applied as value < (exit_below - hysteresis) or value > (exit_above + hysteresis).
    - exit_logic: "AND" (default) or "OR" – how multiple monitor conditions combine for exit.
    - exit_sustain_sec: Seconds the exit condition(s) must hold before auto-cancel.

JsonLogic condition operators (as implemented in JsonLogic.kt):
- Logical composition: and, or, not, all (array of conditions must all be true), any (any true).
- Equality/inequality to keys: eq_key, ne_key.
- Numeric comparisons against literals: lte_key, gte_key, lt_key, gt_key.
- Cross-key comparisons: gte_keys.
- Range: between [key, low, high].
- Statistical: zscore_lt/zscore_gt using SeriesRepo state.
- Temporal state: recently_in(key, seconds) using StateRepo/StateTracker.
- ref/is: direct equality checks against refs.


3) Runtime Data Flow and Components
3.1 Emission of measured values
- Services (e.g., HeartrateService, ActivityRecognitionService) emit CepEvent(topic, payload) to CepBus.
- Payloads live under com.aitech.weartak_civ.cep.model.payloads.* and include HeartRatePayload, ActivityPayload, Spo2Payload, etc.
- CepBus.events is a hot MutableSharedFlow; producers call emit/tryEmit.

3.2 Ingestion into windows and feature store
- CepEngine.start() subscribes to CepBus.events and forwards each event to WindowStore.ingest(evt, featureStore).
- WindowStore.ingest() maintains rolling rings for numeric and array series (DoubleRing/ArrayRing) and writes latest raw values to FeatureStore (e.g., "heart_rate", "ambient.temp_c").
- FeatureStore keeps a KV map of latest values and timestamps and provides helpers to write raw (put) vs derived (putDerived), namespace keys, and read typed values (double/bool/str).

3.3 Tick loop and feature computation
- CepEngine runs a periodic loop at tickHz (derived from engine.window_tick_ms):
  1) featureStore.beginTick() resets per-tick derived log buffer.
  2) For each feature definition:
     - Window features computed in WindowStore: computeWindow, computeMultiWindow, computeSlopeMulti, computeDelta.
     - Derived features computed in DerivedEval.eval():
       - Specialized handlers (wind_chill, zone_min_bpm, mark_state, karvonen_ratio).
       - Numeric/boolean/categorical DSL (key, div/mul/sub/add/max/min/sum/case, lte/gte/lt/gt/eq/and/or/not, categorical bins/labels).
       - Fallback legacy JsonLogic for remaining expressions.
  3) featureStore.logDerivedTick("CEP") prints compact changes for debug visibility.
  4) ruleEngine.processTick() evaluates rules.
  5) checkAndClearAlerts() enforces exit-based auto-cancellation.

3.4 Profiles and computed baselines
- CepEngine.updateHrProfile(yob, hrRest) computes HRmax via ZoneHelper.tanakaHrMax() and populates FeatureStore keys like "profile.hr_rest_bpm" and "profile.hr_max_bpm". DerivedEval may reference these in formulas (e.g., karvonen_ratio).


4) Rule Evaluation, De-duplication, and Throttling
4.1 RuleEngine
- For each rule on each tick, RuleEngine computes cond = JsonLogic.eval(rule.when, featureStore).
- Trigger gating: TriggerTimer enforces sustained_for_sec and hold_down_sec to avoid chatter and re-firing too soon.
- When fired, RuleEngine builds a TriggerContext with the normalized ActionDef and feature snapshot and enqueues it into CepActionDispatcher.

4.2 Dispatcher throttling
- CepActionDispatcher uses a severity-based throttle (INFO: 0ms, WARN: 5s, ALERT: 10s, EMERGENCY: 15s). Key includes ruleId, type, severity, and tags.
- If throttle allows, the dispatcher invokes the appropriate ActionHandler.

4.3 Action handling and alert creation
- LogActionHandler is the main handler for "log" actions.
  - Derives priority from severity unless priority is explicitly provided.
  - Chooses/stores the alert UID (explicit uid or a new UUID).
  - Calls AlertRegistry.tryActivate(ruleId, priority, uid, monitor, exitLogic, exitSustainSec). If an alert for the rule is already active, the handler returns early, suppressing duplicates.
  - Posts CustomEmergencyEvent (isCancel=false) with uid/category/description/priority/sendSms to EventBus for downstream transport (e.g., TAK server, Ditto mesh, multicast, optional SMS in CotDispatchService).
  - Note: A commented timeout-based auto-cancel exists, but the primary cancellation path is exit-condition–based.


5) Cancellation and Duplicate Prevention
5.1 AlertRegistry
- Global registry tracking currently active alerts keyed by ruleId. Each ActiveAlert stores: ruleId, uid, startedAtMs, exitConditions (monitor[]), exitLogic, exitSustainSec, and internal exitSatisfiedSinceMs timestamp.
- tryActivate(ruleId, uid, ...): Returns false if the rule already has an active alert (duplicate suppression), else records a new ActiveAlert and returns true.
- clear(ruleId): Removes the alert, allowing future re-activation.
- allActive(): Snapshot collection for periodic exit checking.

5.2 Auto-cancel via exit conditions
- CepEngine.checkAndClearAlerts():
  - Iterates active alerts.
  - For each, evaluates monitor[] exit conditions by reading the latest feature values and applying hysteresis to avoid oscillation:
    - belowOk = value < (exit_below - hysteresis) if exit_below is present
    - aboveOk = value > (exit_above + hysteresis) if exit_above is present
    - A condition is true if belowOk || aboveOk
  - Combines via exit_logic: "AND" (default) requires all true; "OR" requires any true.
  - If combined condition is true, starts or continues timing; once elapsed ≥ exit_sustain_sec, posts a CustomEmergencyEvent with the same uid and isCancel=true (and a cancellation category), then AlertRegistry.clear(ruleId).
  - If combined condition becomes false again before sustain time completes, exitSatisfiedSinceMs is reset.

5.3 End-to-end duplicate prevention
- TriggerTimer: Debounces initial firing (sustained_for_sec) and adds cooldown (hold_down_sec).
- CepActionDispatcher: Applies severity throttle between consecutive firings with same identity key.
- AlertRegistry: Suppresses repeated alert emissions while an alert is already active for the same ruleId (hard de-dup while in active state).


6) Transport Layer Notes (out of CEP core but relevant)
- CotDispatchService subscribes to CustomEmergencyEvent and sends alert/cancel CoT messages, and optionally SMS.
- Cancel messages use the same UID to clear the original marker (currently coordinated through stored sosAlertUid for manual SOS; CEP-driven events also include uid in the event).
- For multi-alert scenarios, consuming event.uid directly in the sender is recommended to correlate alert/cancel pairs unambiguously.


7) Naming, Keys, and Namespaces
- FeatureStore stores keys using a consistent dotted path convention:
  - Raw measured keys (e.g., "heart_rate", "ambient.temp_c", "activity.state") written via FeatureStore.put() by WindowStore.ingest().
  - Derived features commonly referenced as "features.<id>" (FeatureStore.namespacedId() helps normalize).
  - Profiles (e.g., "profile.hr_rest_bpm", "profile.hr_max_bpm").


8) File/Type Reference (selected)
- Config + compiler:
  - CepConfig.kt – data classes for features, rules, actions, exit conditions.
  - RuleCompiler.kt – JSON parser for engine, features, and rules.

- Engine + evaluation:
  - CepEngine.kt – tick loop, feature computation, rule eval, and exit-based alert clearing.
  - WindowStore.kt – ring buffers and window-based computations; ingest of CepEvent payloads into FeatureStore.
  - FeatureStore.kt – KV store with timestamps and per-tick derived logging.
  - DerivedEval.kt – DSL evaluation for derived features.
  - JsonLogic.kt – rule condition evaluator (operators listed in §2); also SeriesRepo/StateRepo helpers.
  - TriggerTimer.kt – sustained/hold-down gating for each rule.
  - ZoneHelper.kt – HR-related formulas (Tanaka HRmax, Karvonen calculations).
  - RingConfig.kt – ring buffer capacity configuration.

- Bus + payloads:
  - CepBus.kt – shared flow emitting CepEvent<out CepPayload>.
  - Topics.kt & TopicRegistry.kt – topic constants and payload class mapping.
  - payloads/*.kt – sensor payload types (HeartRatePayload, Spo2Payload, ActivityPayload, etc.).

- Actions + alerts:
  - CepActionDispatcher.kt – severity throttling + handler dispatch.
  - ActionModels.kt – ActionDef, TriggerContext, Severity enum.
  - LogActionHandler.kt – TAK alert emission + de-dup via AlertRegistry.
  - AlertRegistry.kt – active alert tracking and de-dup.
  - CepEngine.checkAndClearAlerts() – auto-cancel logic using monitor[], exit_logic, exit_sustain_sec.

- Events + transport:
  - CustomEmergencyEvent.kt – event posted to EventBus (uid, category, description, priority, sendSms, isCancel).
  - CotDispatchService.kt – builds and sends CoT alert/cancel messages (and optional SMS); integrates with TAK/Ditto/multicast as configured.


9) Typical End-to-End Sequence
1. A service emits a measured value (e.g., HR) into CepBus as CepEvent(topic=Topics.HEART_RATE, payload=HeartRatePayload(bpm)).
2. CepEngine’s subscriber calls WindowStore.ingest(), which writes raw values to FeatureStore and updates rings.
3. On each tick, CepEngine computes all configured features via WindowStore and DerivedEval, writing derived outputs.
4. RuleEngine evaluates rule conditions (JsonLogic) against FeatureStore; TriggerTimer ensures sustained and cooldown constraints. On fire, it enqueues a TriggerContext to the dispatcher.
5. CepActionDispatcher throttles per severity and calls LogActionHandler. LogActionHandler de-duplicates via AlertRegistry.tryActivate() and posts a CustomEmergencyEvent with uid and metadata.
6. Transport layer (e.g., CotDispatchService) sends the alert (TAK/Ditto/SMS/etc.).
7. Meanwhile, CepEngine.checkAndClearAlerts() evaluates exit conditions. When satisfied for exit_sustain_sec, it posts a cancel event with the same uid and clears from AlertRegistry, preventing duplicates and cleaning up the downstream marker.


10) Notes for Authors of New Features/Rules
- Use measured keys (from WindowStore.ingest) and derived ids consistently (prefix with "features." where appropriate).
- Prefer derived features for reusable computations; keep rules declarative.
- Include action.monitor[] + exit_logic + exit_sustain_sec on rules that should auto-clear to avoid stale alerts.
- Tune sustained_for_sec and hold_down_sec, and rely on dispatcher throttling + AlertRegistry for robust de-duplication.
